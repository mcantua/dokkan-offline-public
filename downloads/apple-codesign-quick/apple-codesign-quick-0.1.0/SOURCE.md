## Local changes

- `src/bundle.rs`: resources now stream through one 64 KiB buffer per active worker, updating SHA1 and SHA256 in the same pass. Resource hashing never uses mmap or its whole-file allocation fallback. Resource hashes and CodeResources semantics stay the same.
- Added `sign_bundle_controlled` and `Bundle::sign_controlled` accepting a shared `Fn() -> bool + Send + Sync` stop/deadline predicate. Existing APIs use a never-stop predicate. Checks occur at resource chunks, directory entries, bundles, library/executable boundaries and before metadata writes. Scoped Rayon work joins before returning; no detached signer worker is created.
- `src/control.rs`, `src/macho.rs`, `src/signature.rs`: controlled executable signing checks after reading, between thin/FAT phases, at each code page and code-directory slot, around CMS signing and immediately before replacing the executable. Existing entry points retain their API signatures/default never-stop predicate; the file backend adds the explicit supported-input policy below. A cancelled CMS callback regression confirms that the original executable is preserved before replacement. An in-progress syscall/crypto operation and the final check/write race cannot be atomically interrupted; this is cooperative cancellation, not hard realtime or rollback.
- The **file-signing APIs now enforce an explicit backend limit**: at most 128 MiB per input executable and per signed output (including all FAT slices/alignment), and at most 4 MiB per embedded signature, matching App Installer's verifier. A process-wide cancellable atomic lease admits only one file rewrite at a time; native file loading uses fallible exact reservation, 64 KiB reads, length/type checks and an EOF probe. FAT slices and executable hashing/directory work execute sequentially under the lease, preventing nested Rayon wait/deadlock and simultaneous file-sized copies across file signers. FAT slice sums/output growth are bounded and the original input is dropped before rebuilding output. This prevents unbounded multi-GiB executable allocations; it does not establish an exact process RSS limit or guarantee memory availability on every device.
- New fixed typed errors `ExecutableLimit`, `MemoryUnavailable` and `ExecutableChanged` report the file-backend limit, allocation failure and changing source. Callers must present these as technical signing/re-import errors, not missing Apple capability/ownership claims. Existing API signatures remain; the new file limit is an explicit supported-input restriction, not silently streamed executable support. `sign_macho_data` remains a caller-allocated data API with no file-size policy or admission lease; its allocations must not be represented as bounded by this policy.
- `src/error.rs`: typed `CodeSignError::Cancelled`, with a fixed message and no account/device detail.
- `src/lib.rs`: exports the controlled bundle/executable entry points and stop-predicate type, and stops compiling the now-unused private file-bytes mapper. Its original source remains present as published provenance. Executable rewriting remains memory-based under the new file-backend policy; it is not a file-backed/streaming Mach-O implementation.
- Two focused `resource_signing_` checks exercise the actual resource hashing helper (partial/Interrupted reads, matching hashes, I/O failure, logical 4 GiB cancellation), a successful synthetic executable signature, cancellation inside its actual CMS callback before file replacement, an already-cancelled bundle that does not open/rewrite metadata, sparse oversized input rejection without modifying its prefix/length, changed-input rejection, and cancellation while waiting for the file-signing lease. Execution evidence is recorded separately; adding tests is not a passing-test claim.

The patched Cargo manifest adds no dependency or feature. The root path patch selects this same library for direct and isideload consumers. Matching corresponding source and relink instructions remain required with every distributed binary.
