# Trusted USB remote-pairing bootstrap

This small Mac helper creates the strict version-2 remote-pairing credential required by App Installer. It runs only after the reviewed setup wizard has selected a physical USB iPhone and the already-approved routine pairing step is invoked. It does not ask for Apple-account passwords, change signing certificates, install an app, change VPN settings or upload anything.

The existing official idevice_pair1.1.0 export is a different, unpinned format. Its standard Remote pairing file is **not accepted** as an authenticated App Installer version-2 record. This helper uses the patched idevice implementation to verify SRP-M6 accessory identity, capture its Ed25519 public key and identifier, and serialize only a verified pinned record. Subsequent phone connections must verify that exact peer signature; discovery and VPN routes do not authorize a substitute identity.

The reviewed wizard supplies `--repo-root` and the locally confirmed `--device-udid`, together with explicit `--consent`. Do not paste the identifier or exported record into chat. Default invocation or `--help` describes the helper without device action. `--version` returns only `app-installer-rp-bootstrap 0.1.0` before project/USB/consent handling, for the cloud packager’s mechanical binary check. Only the system Unix usbmuxd socket is used; USBMUXD_SOCKET_ADDRESS overrides, network rows and simulator identities are not accepted. Existing macOS USB pairing records are read through usbmuxd into memory and are never copied to files. A verified TLS session confirms the selected live hardware identity before remote pairing begins.

Initial remote pairing is explicit over that trusted USB service. The helper never uses an automatic reconnect/re-pair fallback. The official idevice_pair trusted-USB implementation documents that the phone already trusts this computer and does not ask again; its callback supplies the protocol value `000000`. This helper uses that same value only after verifying the selected physical USB iPhone and its authenticated Lockdown session. The library also selects it when the authenticated service reports `awaitingUserConsent`. There is no six-digit dialog, guessed user code, untrusted network pairing entry point, Apple-account credential prompt or certificate-verification fallback. SRP-M6 and the captured accessory signature must still authenticate before export.

Before publishing a newly created credential, the helper closes the setup stream and opens a fresh authenticated USB Lockdown/service connection. That new connection must complete the remote-pairing handshake and verify the exact captured peer pin with the serialized host identity. A reconnect, handshake or pin failure publishes no file and does not retry pairing or rotate trust. This follows the official tool’s second-connection verification step; it is a cloud implementation postcondition, not proof that Tin’s phone pairing failure has been fixed.

The only credential output is:

`app-installer/device/private/secure-rp/pairing.mobiledevicepairing`

Both private directories must be owned by the current user with 0700 permissions; the complete credential is committed atomically as 0600 without replacing any existing file or symlink. Before any device activity or key generation, an existing credential must be a bounded, current-user-owned 0600 regular file with one hard link and a strict version-2 peer pin; symlinks, malformed records and broader permissions cause a safe stop. A valid existing record is reused only after its pinned peer signature is verified against the selected, authenticated USB iPhone. It is never rewritten. Failed reuse never falls back to creating a new identity or changing trust. It contains the host identity/private key, authenticated peer pin and discovery material. Keep it private and transfer it only through the approved protected import route. It never belongs in GitHub, cloud artifacts, logs or screenshots. One fixed private pending filename is cleaned on ordinary failure; an interrupted prior export is preserved and causes a safe stop for reviewed recovery. Existing Lockdown records and other private setup/build files are untouched.

stdout contains fixed status lines only. All dependency tracing is disabled at compile time in development and release builds; panic/error output is fixed and contains no raw device error. No private key, PIN, identifier or record is printed. Export bytes use a zeroizing memory buffer. The0600 output is intentionally persistent for the authorized import; the helper does not promise erasure of all operating-system memory copies.

The cloud packaging recipe will supply an architecture-compatible, hash-pinned Mac binary with matching complete source and notices. No Rust toolchain or SDK download is required on Tin's Mac just to run it. Build/packaging and actual USB execution have not been performed as part of authoring this source. Two grouped offline argument/file-integrity tests cover explicit consent, the trusted-USB callback, bounded strict-record reuse and no-overwrite/symlink protections. Both passed in one offline `cargo test --offline --locked --bin app-installer-rp-bootstrap` invocation (2 passed, 0 failed, 0.01 seconds). These synthetic checks do not prove a live Mac or iPhone pairing succeeds.

## Safe live pairing diagnostics

The helper emits and flushes only fixed public stage tokens. `RP_BOOTSTRAP_STARTED` confirms Rust entered the operation; absence of that token does not prove the macOS launch/security assessment completed. The pairing observer reports consent, SRP proof, peer-record exchange and authenticated peer-identity processing through `PairingStage`; these callbacks carry no identifiers, keys, messages or payloads and do not change the protocol. The operator wrapper must forward only its exact stage allowlist, never raw captured output.

The 180-second asynchronous pairing deadline has a distinct fixed timeout failure. Returned typed errors are mapped to fixed rejection, SRP-proof, protocol, USB-transport or peer-identity failures; error string payloads are never formatted or forwarded. A timeout does not prove the device rejected pairing, and the last public phase does not establish Tin’s original failure cause. Synchronous filesystem/crypto work and pre-main macOS launch assessment are outside Tokio’s cooperative timeout; the wrapper owns any separate process wall-time deadline and must preserve existing files on an unknown/interrupted outcome.

One focused synthetic diagnostics regression passed separately: 1 passed, 0 failed, 3 prior tests filtered out, 0.00 seconds. It checks fixed stage mapping, typed failure/privacy behavior, timeout-versus-error routing and success. Exact helper Cargo/lock/main hashes were captured before and after that run and were unchanged. It does not perform USB or protocol authentication; the vendor’s separate signed-handshake regression and genuine cloud compilation retain their own evidence scopes.
