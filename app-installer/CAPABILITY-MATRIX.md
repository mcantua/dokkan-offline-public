# IPA capability support and actual limits

This matrix describes implemented signing/provisioning logic, not a claim that an arbitrary re-signed commercial app works. No Apple account or phone operation has been run. A supported entitlement must be present with compatible values in the **actual profile returned by the selected team's authenticated Apple session**, and the signed output must pass the independent verifier. Free/paid availability is decided by Apple, never inferred from an allowlist or bypassed.

The signer emits required, reconciled grants only; it does not copy every profile privilege or silently remove unavailable features. Unknown entitlement keys with legal bounded plist structures are eligible when the real profile explicitly grants them. Missing/mismatched grants stop signing with a fixed explanation.

| Capability | Implementation | Account/resource conditions and genuine limits |
|---|---|---|
| Application/team identity | Deterministic per-team main/extension IDs; preserve a selected-team-owned original ID when available, and preserve the actual installer self ID | Third-party globally registered IDs cannot be claimed by another team. Existing installed copies must match a known owned identity; ambiguous/cross-team copies are refused instead of duplicated. |
| Default Keychain | Third-party apps regenerate the default group from the actual profile AppIdentifierPrefix + signed bundle ID. Installer self-updates require the actual running installer's exact application/team/Keychain identity and original team; unsigned new self IPAs inherit those existing groups | A self-update that would change the identity is refused before signing/installing. Old app-private data belongs to the old signing identity; a re-sign cannot grant another team's private data. The new self guard still needs its affected cloud and real-phone verification. |
| Shared/custom Keychain groups | Preserve exact required groups when the actual profile authorizes each group; main/extensions can share the same authorized exact group | Hardcoded foreign-team prefixes cannot be silently replaced. A mapped identifier is not proof that existing app code uses it; no unverified binary rewriting or sharing-identity substitution is performed. |
| App Groups/shared containers | Read exact requested IDs, request APG3427HIY, reuse/create exact IDs through AppGroupsApi, bind all groups in one array, verify actual profile grants and preserve exact values | Exact group must be owned/registrable by selected team. Apple may refuse a globally owned foreign group. No source constant is quietly hashed/renamed; generic hardcoded foreign groups genuinely need original developer cooperation or source changes. Availability is Apple's profile decision on free/paid accounts. |
| Associated domains | Request SKC3T5S89Y, preserve requested domain/service values only if profile grants them | Domain AASA must authorize the actual signed team+bundle ID. Signature metadata cannot alter somebody else's website. Preserving a team-owned original App ID avoids unnecessary service identity changes. |
| Game Center | Request gameCenter and preserve granted entitlement | Existing App Store/game registration and backend identity may still be required. A new signed ID does not become the original game's Game Center identity. |
| Inter-App Audio | Request IAD53UNK2F and preserve granted entitlement | OS deprecation/removal and source app behavior remain runtime constraints; profile grants cannot restore a removed OS API. |
| HealthKit, HomeKit | Request HK421J6T7P/homeKit; preserve exact required grants/arrays | Apple account/profile eligibility, user consent, usage descriptions and real device support still apply. No permissions are fabricated. |
| Hotspot configuration, Multipath | Request HSC639VEI8/MP49FN762P and preserve actual grants | Account entitlement eligibility, external network conditions and hardware remain necessary. No personal network used for verification. |
| Network Extensions, Personal VPN | Request NWEXT04537/V66P55NK2I and preserve exact granted provider/API types | Apple entitlement eligibility and provider extension signing required. Free accounts cannot invent a Network Extension grant; LocalDevVPN remains the separate App Store tunnel for installer transport. No entitlement/security bypass. |
| NFC | Request NFCTRMAY17 for reader-session formats and preserve authorized values | Device support and Apple-controlled restricted uses (payment/HCE/etc.) cannot be inferred from the generic reader capability. Other NFC grants require explicit profile authorization. |
| Siri, AutoFill provider, ClassKit, Wireless Accessory | Request SI015DKUHP/CPEQ28MX4E/PKTJAN2017/WC421J6T7P; preserve real grants | Required app extensions, usage metadata, hardware/MFi or managed-service eligibility and user consent remain runtime requirements. |
| Data Protection | Map the source's requested default protection to documented dataProtection settings; preserve actual authorized value | No silent weakening to make signing succeed. Installer credentials remain device-only Keychain protected independently. |
| Increased memory, increased debugging memory, extended virtual addressing | New configure_new_memory_capabilities adapter submits the exact documented memory/debugging/VA capability enums together on newly created App IDs, then requires actual resulting profile grants. Existing granted values are preserved | Existing App IDs are never subjected to a blind REST relationship replacement that could disable their other configured capabilities. Enabling missing memory grants on existing IDs still requires a merge-aware adapter or Apple portal configuration; current profile-backed support is not called unsupported. Apple/account/device limits still apply. |
| APNs/push | Preserve the exact aps-environment when selected profile grants it | Current signing mode obtains development profiles. A production request is not silently changed to development. Production push needs a legitimate compatible distribution profile/certificate mode plus provider/backend control; that distribution mode is not implemented here. Portal push enablement has a distinct CSRF/session-primed web operation, so no guessed updateAppId flag is sent. Existing configured development profiles are supported. |
| iCloud/CloudKit/ubiquity | Preserve exact requested container, service, environment and KV-store grants from an already configured selected-team profile | Containers are owned external resources; another team's data cannot be transferred by renaming an entitlement. Exact existing-container list/bind APIs were identified, but use the developer web portal's CSRF/cookie session rather than the current GSA/Xcode session. A web-session adapter is not implemented; there is no guessed endpoint/auth translation. This is not universally impossible. Preserve owned original App IDs and existing bindings where possible. |
| Apple Pay/Wallet | Preserve exact merchant/pass identifiers when actual profile grants them; Wallet feature request supported | Merchant/pass ownership, certificates and payment/backend registration remain required. Exact existing-merchant binding operation was identified; its separate web-portal session adapter is not implemented. No merchant impersonation or silent substitution. |
| Sign in with Apple, App Attest, app-specific managed entitlements | Generic profile-backed exact preservation, including arrays/dictionaries/scalars | May require selected-team/service approval and backend configuration. New automatic service-specific enablement adapters are not implemented for every Apple-managed capability. A legitimate actual profile can authorize values; otherwise fail explicitly. |
| StoreKit purchases, App Store receipts, FairPlay | Not a provisioning entitlement that can be recreated by re-signing | Valid store receipts, service ownership and decrypted legally obtained executable remain separate requirements. Encrypted Mach-O is rejected; no decryption or receipt/authentication bypass is implemented. |
| Nested Watch/Clip apps or unusual signed layouts | Currently rejected by structural validator pending recursive architecture/provisioning support | This is a supported-layout implementation limit, not a claim every such package is impossible. iPhone app + audited direct extensions are current scope. |
| Private/platform-only Apple entitlements | No blanket acceptance or blanket copying; only actual selected profile authorization is accepted | A normal personal developer certificate cannot create platform authority. Apple approval/appropriate authorized profile is required where legitimate; no platform-security bypass. |

## Verification boundary

Offline tests cover grant preservation, refusal of privilege widening, unsupported exact group ownership, production/development push mismatch and structured grants. They cannot prove Apple's live account response, remote domain/provider behavior, Keychain runtime, VPN pairing or device installation. Live verification requires real authorized account/device steps and must never be labeled complete before they actually succeed. Tin's MacBook/personal network require a separate exact-step explanation and explicit approval before use; no phone install is authorized by this matrix.

## Required target scope from available source

Read-only inspection of unit-creator/ios-objc/build-ipa.sh shows com.dokkanunitcreator.ios built ad hoc without a custom entitlements file. Host.m uses ordinary native Keychain with no explicit shared access group. Camera, Photos and Files are sandbox/usage-description permissions, not special provisioning grants. No app groups/iCloud/APNs/Network Extension requirement appears in that source. The Installer itself needs regenerated identity, an exact default Keychain group, ordinary Face ID/BGTask/notification permissions, and the separate LocalDevVPN transport; it does not request its own Network Extension entitlement. These known target provisioning requirements are implemented. The actual user's signed Unit Creator IPA must still be inspected when available; ChatGPT did not rebuild or edit Claude's project.

## Portal adapter evidence and limits

The pinned Apache-2.0 reference at downloads/apple-portal-reference/SOURCE.md and MIT Fastlane source show exact list/assignment APIs for existing iCloud containers/merchants and the distinct push operation. They prime CSRF state and use an authenticated developer **web** session. This project has a GSA/Xcode DeveloperSession, not that cookie/CSRF session; endpoints are not blindly translated to unrelated QH65 paths. The reference SDK's third-party relay is NOT used, and no Apple credentials/tokens have been sent to it. An Apple-only web-session adapter or the user's legitimate portal configuration can be added; already configured selected-team profiles are supported today, especially when preserving their owned original App IDs. No production distribution credentials are stored or requested in the cloud.
