# IPA validation review notes — October 28, 2026

`core/src/archive.rs` supplies `validate_and_extract(input, destination)` before the signing library can inspect an IPA. It returns a `ValidatedIpa` with main app directory, original bundle ID, display name and extension IDs. The staging tree is removed when that owner is dropped. Errors are fixed messages and never expose archive paths or underlying system diagnostics.

The caller passes a new UUID/counter staging child in its trusted private container. Existing destinations are refused without changes. The importer first copies a coordinated Files URL into a protected private UUID file. The engine checks that source is in its own imports/sources directory and is not a symlink, then passes only `validated.app_dir` to `Application::new`. It does not call the library's generic ZIP extraction on untrusted input. Successful original-source retention happens separately after the device confirms installation.

Validation covers:

- ZIP32/ZIP64 EOCD limits before `ZipArchive::new` can allocate attacker-controlled metadata. Split-disk and self-extracting ZIPs are unsupported.
- Declared central-directory entry count must match the ZIP reader's entry count. This catches exact duplicate names that zip 8 internally coalesces in its IndexMap.
- Strict UTF-8, bounded path depth/component/aggregate metadata sizes, no absolute/traversing/backslash/drive-like/control-character paths, full Unicode case folding and canonical normalization, no filename aliases or file/directory conflicts.
- Symbolic links, special files, encrypted ZIP entries and nonempty directory entries are rejected. Extraction creates ordinary files exclusively; directories and files use private permissions. No archive-supplied permissions or timestamps are restored.
- 100,000 entries, 32 MiB central-directory and path storage budgets, 4 GiB individual uncompressed file, 16 GiB compressed archive/total expanded bytes; entries above 1 MiB with more than 1000:1 expansion are rejected. Every extraction stream is limited to the declared size plus one byte, with size/CRC verification.
- Exactly one `Payload/*.app` with a correctly named Info.plist. Bundle IDs and executable names are validated. Main/extension/framework executables and dylibs must have bounded Mach-O commands, arm64 code, an iPhoneOS deployment command, and no encryption. Fat slice offsets/overlap and segment bounds are checked. arm64 simulator/macOS binaries are rejected.
- Nested `.app` bundles (including Watch companions) are refused because the current engine does not recursively provision/sign them. Uppercase/mixed-case code suffixes are refused to avoid mismatches with the signing library's case-sensitive traversal. Symlink-based/versioned frameworks are unsupported. These are deliberate compatibility limits, not silent stripping.

Two offline grouped regression tests passed in two invocations. The second expanded the corpus after source review: unsafe paths, canonical/case aliases, duplicate-central-name coalescing, forged ZIP64 count, high-ratio deflate data, encrypted main/extension, symlink mode, simulator platform, valid thin arm64 identity, cleanup on failure/drop and existing-destination preservation. No real IPA, account, VPN or device was used. After these tests, the explicit nested-app/case-suffix policy above was added at the engine agent's request; it still needs the final integration compilation, and that last policy has not had a separate runtime test. No further test repetitions are needed this session.

This is bounded structural validation, not proof that arbitrary imported machine code is safe or that every valid IPA format is supported. FAT/ZIP64 parsing has source review and compile coverage; the current corpus is not an exhaustive parser fuzzer. The private-container trust assumption matters: the app must not expose its staging/import paths through file sharing or app-group writers. The build agent/root should keep these paths excluded from cloud backup and protected while locked.
