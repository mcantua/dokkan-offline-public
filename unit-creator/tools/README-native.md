# Cloud native build tools

`python3 tools/setup-native-tools.py` provisions the pinned x86_64 Linux compiler, iPhoneOS16.5 SDK and matching Java21 compiler/Java8 API signatures beneath ignored `downloads/unit-creator-tools/`. `tools/javac --release 8` sets the correct JDK `java.home`, rather than accidentally using the installed JRE without `ct.sym`. This step does not build or sign an app. The Linux iPhone recipe's existing SDK27.1 display mark is distinct from actual SDK16.5 compilation; the independent cloud-native workflow uses genuine Xcode27.1 instead.

`python3 tools/setup-smali.py` separately downloads the pinned public smali/baksmali2.5.2 dependency set into ignored `downloads/unit-creator-smali/`; `--check` validates every saved SHA256 without downloading anything. Provenance stays in `SOURCE.md`, not JAR copies. These public tools contain no app or signing data.

After Tin authorizes builds and supplies the original base APK/release key privately, `build-from-release.sh` checks the base release certificate, disassembles its primary dex, applies the current Sparking APK setup and post-activation master-database hooks, reassembles, and checks the instructions survived a second disassembly. An explicit `CLASSES_DEX` replacement receives the same required hooks. Missing/ambiguous classes/methods or changed pinned tools fail the build before APK packaging. The two narrow patchers leave unrelated class code and original private activation paths intact. Public tool setup is explicit; the release script does not download unknown tools or private inputs.

The focused synthetic verification assembled a genuine tiny dex with both real method signatures and original monitor/exception paths, patched/reassembled it, and disassembled it again to verify both hook classes and instruction idempotence. It also rejected overwriting an existing output. This proves the toolchain and narrow hook integration; it is not an original APK build, Android launch, original game import, signing or device test. Those still need the private release inputs and actual platform execution.

## Coexisting development APK

`python3 tools/setup-android-tools.py` provisions official SHA256-pinned SDK35/build-tools35/platform-tools for x86_64 Linux. Add `--ndk` for the independent Offline engine's native build. It uses Google public tool archives under ignored `downloads/android-sdk/`, never Tin's computer or signing identity.

When builds are authorized, `python3 tools/build-development.py` builds the actual retained original primary dex, the latest narrow hooks and current `dock/src` native patches against real Android SDK declarations. It includes the full real UI, both supplied databases and original four-ABI zstd JNI libraries. It regenerates only the three missing original resources at their exact original IDs while retaining all original components/permissions. The loopback player may use cleartext HTTP; other cleartext hosts remain disabled.

This is version2.36.3/code128 in a distinct `com.dokkanunitcreator.development` package, provider authority, public Downloads folder/marker and private development signing identity. It coexists with the release app and does not update its release identity. Only the current complete candidate becomes `out/Dokkan-Unit-Creator-Development-2.36.3.apk` after signing, alignment, CRC, resources and version checks; previous working output survives earlier failures. The ignored development key/password are kept privately for later development updates and are never included in source, download bundles or logs. `out/development-android-check.json` distinguishes actual checks from unverified device behavior.
