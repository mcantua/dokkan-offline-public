# Data-free Android native local-save manager

This development host is part of **our own original Offline Dokkan game**. It exercises real JNI/C/SQLite progression, snapshots, save export/import and normalized Offline Creator definition import/export. There is one canonical player and one editable Creator workspace. Eclipse/Sparking identify imported database, asset and download sources; they are not game modes or separate progressions. Playable battles and finished game screens remain unfinished. Interception of another game client is not a project requirement.

The **Import data source** setup dialog identifies Eclipse or Sparking, then offers **Download database** or **Import file**. Local imports use the system file picker for a user-selected master database/archive. The main player screen has no source selector, source-specific player name or source-specific save-export filename. Player saves and settings-only unit JSON also use explicit file pickers. Master import streams/hashes bytes off the UI thread, checks SQLite integrity/required tables/columns through Android's supported read-only framework API, probes the native core, and refuses a changed content version over an existing player without a migration. Sources are never modified. A new profile has zero invented stones/cards; snapshots show real persisted balances/counts. Native file-transfer scratch is removed after completion.

Explicit unit-file import accepts the normalized `offline-dokkan-definition` format/schema1 and calls actual `creator.finish` to place one owned custom copy in the collection; it does not disguise an unprojected `dokkan-unit-forge` project as that format. Settings/identity/version/credit and master references are validated by the core. Re-import deduplicates by definition identity and never mints another direct-owned copy; exports are exact `creator.export` documents. Forms/custom assets and full game rendering still require their explicit integration paths. Save import validates the candidate before replacing live state.

The app requests INTERNET for explicit website database downloads and no broad-storage permission. External local files use explicit system pickers. There is no startup download or background sync, and the embedded Creator still blocks remote resources/navigation. File transfers and native engine calls run on a serial worker; the UI remains scrollable and accounts for system bars. This does not establish physical folding/keyboard/gameplay behavior.

This explicitly labeled development manifest is debuggable. The Creator enables WebView inspection only when Android's `FLAG_DEBUGGABLE` is set, so the owned hosted emulator can inspect the actual rendered shared UI and native responses. A distribution manifest must omit `debuggable`; this package is not a hardened release.

**Open Unit Creator** opens the actual shared editor as an internal screen of our Offline Dokkan app. `OfflineCreatorActivity` serves only audited app UI/fonts at a fixed private HTTPS origin, blocks external resources/navigation, and exposes only the narrow `OfflineCreator` capability. Selected master queries are read only and validate table/column identifiers against that actual imported schema; no SQL, private path, generic core operation, reward, network or key service is exposed to JavaScript.

`OfflineCreatorSession` keeps full editable projects in the single canonical private SQLite workspace. Its internal source identity comes only from the active validated master, not an activity intent or selectable gameplay mode. Saves reject older conflicting edits while retaining incomplete card settings; named versions use revision checks, keep at most ten total versions/40 MiB, and maintain only one automatic safety copy. Large project text uses direct SQLite string reads to avoid Android's small CursorWindow limit. Back waits for the actual shared UI save before closing. These editable workspaces are separate from exported player-save files.

Finish needs no project export/file move. Native prepare binds a durable project revision to its master hash, definition identity/version and persistent retry command, and proves every omitted unsupported baseline row against the read-only master. The existing shared `creator-project.js` projects that native snapshot; native finish independently compares the entire projected card/tables/context and rechecks the snapshot under a workspace transaction. It persists the intent before actual `creator.finish`, then confirms the permanent owned instance and refreshes the live library. The stable command adds `:collection-v1` so earlier registration-only intents cannot collide with this operation. Forms/custom art/runtime bindings remain explicit unsupported finish errors; their full editable projects are retained. Finishing updates newest-created state and immediately makes one permanent custom-unit instance available in the owned collection for teams. Replaying the same definition does not mint another copy; a consumed instance is not silently reminted. The optional summon banner remains **not configured** until a trusted complete catalog allocation exists. No pool weights/rates are fabricated.

The master picker also accepts the reviewed plaintext SQLite ZIP/APK archive paths through `OfflineMasterArchive.Stage`. The temporary extracted file still passes the existing SQLite/schema/SHA/core probe before publication; changed content over an existing player remains rejected. Temporary sources/database/sidecars are cleaned, and the selected external file stays untouched.

After provisioning the pinned public SQLite source, Android SDK35 and NDKr28b:

```sh
bash offline-dokkan/mobile/android/build-native.sh
bash offline-dokkan/mobile/android/build-host.sh
```

`build-native.sh` builds arm64-v8a and x86_64 for API26+, using the public pinned SQLite3.50.4 amalgamation with extension loading disabled and hidden symbols. It does not link Android's non-public system SQLite ABI. Both ELF and APK library alignment target 16 KB pages. CMakeLists.txt provides the same source target for a normal Android NDK/CMake build.

Unchanged SQLite compilation is cached by exact public source, NDK pin, target and flags; each ABI retains only its current object. Native receipts pin source and library hashes. Packaging refuses stale/mixed libraries or source that changes during compilation/packaging, so a development checkpoint cannot accidentally ship an earlier engine.

`build-host.sh` packages version **0.1.0 / code 1**, using the shared ignored **cloud development identity**, never Tin's release key. It includes only our code, public SQLite and notices; no game database/assets/app or private material is bundled. Output is the single latest ignored `build/Offline-Dokkan-Save-Manager-development.apk` plus a measured receipt. It must remain labeled development until real install/launch/file-flow checks pass. Unit Creator's version2.36.3/code128 belongs to that separate app and is unchanged by this host version.

The next build also stages `../../creator-ui/build.py` and includes only its exact hash-audited UI manifest. Embedded master tables, source catalogs, game thumbnails and databases are excluded; references come from the selected master at runtime. The existing packaged checkpoint predates this embedded Creator source, so it is not evidence that the new native flow has run. Android SDK35 source compilation and shared-UI/actual-master/core checks are separate from the next hosted Android runtime check; no new package was generated for this integration.

The schema7 cloud checkpoint compiled/linked both genuine NDK ABIs with warnings as errors and compiled the native UI against the actual SDK35 jar. The data-free APK passed signature/alignment and archive-content checks. It has not been installed/launched here: this cloud environment has no `/dev/kvm`. Canonical storage is `files/offline-dokkan/local-player/`, with `player.db`, `creator-workspace.db` and its exact validated master. Native preferences `active.source`/`active.sha256` and an atomic-promotion recovery receipt pin imported content; source changes cannot create a second player. One unambiguous earlier development save is adopted through read-only native SQLite backup, including committed WAL rows, into one fresh stage followed by atomic directory promotion. The prior directory remains the single recovery copy. Existing canonical saves without trusted selection, multiple legacy players, missing masters and content mismatch stop with a recovery message; nothing is silently merged or deleted. SQLite backup is bounded to 512 MiB/30 seconds and verifies integrity and the player content identity before promotion.

The canonical-store boundary passed one Linux Java→JNI→public SQLite3.50.4 scenario using the actual store class/native backup with a minimal host preferences/context adapter. It retained uncheckpointed WAL progress and editable projects, preserved original DB/WAL hashes, rejected mismatched content/ambiguous legacy/orphan canonical states, and refused destination overwrite. Volatile SQLite shared-memory read marks are coordination state, not immutable source data. Actual SDK35 Java and NDK/API26 C source compilation passed separately. This is not Android UI/runtime proof; the prepared hosted scenario remains pending.

**Characters** reads the actual persisted player snapshot and shows owned names, level, Super Attack level and lock state. Created/tournament names come from the owned definition version; ordinary names come from the active read-only master. Lock/Unlock calls the restricted `card.lock` operation. **Teams** edits Team 1 through actual owned choices, preserves the first selected member as leader and allows up to six distinct instances. Saving/clearing calls `team.set`; ownership and duplicate checks remain authoritative in the core. No raw ID entry, synthetic cards or reward grants are exposed. The same pending hosted integration scenario opens the actual collection, saves the finished custom unit into the team and verifies membership after process restart. Native Finish recomputes current owned availability from `profile.snapshot`, so a cached successful command cannot make a consumed unit look usable.

Native website database setup uses `OfflineDatabaseDownload` and the same exact HTTPS URLs as `content/source_downloads.py`. Android defaults verify TLS certificates/hostnames; redirects, encoded responses, empty/truncated/oversized data and a non-SQLite header are rejected. Streaming runs on the existing worker into one fresh private stage, computes SHA-256, and is capped at 512 MiB, 30-second connect/read timeouts and five minutes overall (plus an in-flight read timeout). The actual SQLite/schema check runs before the confirmation. **Download alone does not activate data or create/change a player.** The explicit **Use downloaded database** confirmation reuses the existing master validation/hash/native probe/pin pipeline; an incompatible active save remains untouched. Cancel, destruction and failure close only the fresh stage. A Sparking encrypted response is rejected early with a plaintext-import message; no keys/decryption path is supplied. Source code compiled against actual SDK35; live provider download/UI runtime remains pending in this cohort.

The gameplay foundation adds three scoped page operations on the existing serialized native session:

- `offlineGameSnapshot {}` returns the actual local player snapshot.
- `offlineCardStats {instanceId}` calls actual owned `card.stats`; IDs are safe positive integers.
- `offlineTeamSet {slot,members,intentId}` uses slots0–19, up to six distinct owned instance choices and a stable 1–100-character `[A-Za-z0-9_.:-]` intent. The core command is `game-team:<intentId>`; the reply is a refreshed actual player snapshot. No reward/configuration/grant operation is exposed.

`nativeBattleOperation` is a separate Java/native-only entrypoint on `OfflineCreatorActivity`/`OfflineCreatorSession`; neither `offlineBattleRead` nor `offlineBattleCompareSwap` is accepted by public `postMessage`/`call`. It is reserved for the future isolated trusted battle coordinator. Its completion runs on the session worker, so callers dispatch UI work to the main thread themselves.

- `offlineBattleRead {}` returns JSON null or `{token,data}`.
- `offlineBattleCompareSwap {expectedToken:null|string,data:string}` returns a fresh opaque UUID token or false on conflict.

`OfflineBattleStore` owns fixed private `battle-slot.bin/.pending/.lock` paths. An in-process guard plus cross-process file lock protects read/CAS; writes use a fresh0600 stage, forced file sync, atomic same-directory rename and directory fsync. Crash leftovers are discarded only under the lock; malformed/foreign current data is preserved and rejected. Native source/content/profile metadata, payload SHA-256, strict UTF-8 and configuration/state content IDs bind the slot; the JSON envelope is limited to4MiB and configuration to512KiB. This is private state durability, not proof of battle victory or authorization to award anything. Legal-intent replay, trusted planning and verified settlement remain the coordinator's responsibility. Native runtime/durability proof and gameplay-screen wiring remain pending; this batch only compiles the source with the actual SDK35.
