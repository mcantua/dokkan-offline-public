# Own native local-save host

This is an actual native host for the own SQLite player engine, not the original Dokkan game client or a claim that battles/scenes already run. Android and iPhone use the same C engine and whitelisted bridge. The corrected native screen creates/opens one Offline Dokkan player and imports/exports validated saves. Eclipse/Sparking appear only as content providers during data setup; there is no gameplay mode selector or separate provider-based player.

Distributable Offline Dokkan packages contain **no Bandai/game database or game assets**. Each person imports their own master database through Android's document picker or iPhone's Files picker. Native hosts validate the real SQLite file, create a private immutable snapshot, calculate its SHA256 identity and persist the selection; player saves remain pinned to that content. Selecting a different master does not silently migrate or overwrite a working player. Original files are read-only and never modified. iPhone uses a consistent SQLite backup transaction, including a source WAL, rather than copying live database bytes.

The importer also accepts the person's ZIP or APK through the same picker. The public-zlib archive helper selects only the fixed Eclipse/Sparking database entry, validates ZIP structure/CRC/limits into a fresh private stage, then runs the same SQLite/schema/hash import. It extracts no game resources or keys. The iPhone wrapper retains read-only source descriptors, checks source identity/size/modification time, removes only its own staging file, and never treats extraction alone as a validated master.

`setup-sqlite.py` downloads the official SHA256-pinned public-domain SQLite3.50.4 amalgamation into ignored `downloads/sqlite-amalgamation/source/`. Mobile targets compile that source with thread safety and extension loading disabled. Android never links the platform's private SQLite library. Public tool/data provenance lives in `downloads/*/SOURCE.md`; no keys, source databases or native packages are committed.

The independent hosted native check in `unit-creator/cloud-ui/` uses an explicit `OD_CLOUD_FIXTURES=1` build setting to inject the private reconstructed committed browser snapshots for actual native host testing. The resulting hosted app is a non-distributable test fixture. Production `ios/main.m` has no bundled-data path when this setting is absent: it opens the user-import library and displays the Files import action. The native XCTest exercises actual engine creation/reopen, one canonical player, incompatible-source rejection preserving progress, the real master importer, unsupported-operation rejection, rooted content on Darwin, and a real native screen. It does not invent rewards, playable battles or protocol success responses.

The next source cohort adds **Open Unit Creator** to a ready local player. It packages the actual shared Creator controllers through `python3 offline-dokkan/creator-ui/build.py`, using only authored screens, fonts and licensed dependencies. Game tables, databases and catalog snapshots are excluded. The iPhone controller serves those resources at `app://local/` and exposes only the same-origin, main-frame `OfflineCreator` capability. It does not expose the standalone Creator's file, network, keychain, arbitrary SQL or game-install services. The selected user's native master is opened read-only; queries use validated table/column names and bound values. The native view follows its safe-area bounds when the window changes.

Editable projects and settings remain in a separate private atomic JSON store pinned to the selected content identity. A project may use up to20MiB; requests allow24MiB of envelope space. Saved versions retain at most10 total entries/40MiB per unit, including at most one automatic safety copy. Restore checks the current revision before changing the draft. Failed writes preserve the current state.

Finish first pins a durable project revision, source identity, definition ID/version and stable native command. The shared strict projector supplies a candidate definition; native code independently checks the entire projection against that exact saved draft before calling the actual core's `creator.import`. Stale drafts, modified baseline tables, forged projections and client-selected core operations are rejected. Existing creator credit and stat policy come from the previous core definition, rather than imported author text. A persisted receipt makes retries idempotent; a fresh `creator.library` read supplies current newest/featured status. This registers supported settings in the local save. It **does not configure a drawable summon banner**, execute original-game scenes, or silently accept custom resource/form/runtime features that are still unsupported; the full editable project is kept.
