# Verified local content

`content.h/.c` is a portable POSIX file resolver for the host's verified manifest references. It never downloads anything or guesses stage dependencies. The host selects the imported source and a distinct private app cache directory; clients cannot supply roots, hashes or an arbitrary `assets_ready` assertion.

`od_content_resolve` walks every relative path component with `openat` + `O_NOFOLLOW`, rejects ambiguous/traversal paths and nonregular files, checks exact length and SHA-256 while streaming into a private staged file, syncs it and atomically publishes the content-addressed cache file without replacing an existing file. Only a newly verified read-only descriptor is returned, at offset zero. The original file stays untouched. Identical content is reused even if its original source is gone. Malformed/corrupt existing cache entries fail explicitly; no personal files are deleted or silently adopted. The cache root must remain app-private; callers must not expose a writable descriptor to game code.

`od_content_require` accepts a nonempty complete dependency list resolved by the trusted host and verifies every file before that host may start a run. An unknown/empty dependency list fails. This cannot infer undocumented dependencies from a map ID or establish the game's HTTP/asset manifest format. Real master/manifest mapping and game-hook integration remain separate.

## Imported full-game asset catalog

`export_asset_catalog.py MANIFEST OUTPUT --package com.sparkingDokkan.GLB --version 6.6.0` imports the completed Android export's path/size/SHA256 manifest into an immutable working SQLite catalog. It strips only the observed Android files-directory prefix, retains the engine's `assets/...` paths and rejects duplicate/traversal/invalid records before replacing an existing catalog. `assets/User/` is excluded so player/patcher settings do not become game content. The catalog contains references, not game file bytes or keys, and stays private outside Git.

`lookup_ref(catalog, path, expected_manifest_sha256)` pins the catalog to its exact input manifest and returns the same `path`, `bytes`, `sha256` fields consumed by `od_content_ref`. The existing native `od_content_resolve` still has to verify actual bytes; a catalog entry does not mark files ready or prove iOS format compatibility. No data is downloaded or source file changed by this importer.

The supplied export yielded36,087 retained asset references (26,281,008,348bytes) and63 excluded User records. The actual current master reference is `assets/sqlite/current/en/database.db`,114,827,264bytes, SHA256 `f37296ef05e31000d9868741b18525a5d41311ccc152acb82c848b7b1c8ef14d`. One combined targeted scenario checked this real reference, private-state exclusion, traversal rejection and preservation of the input/existing catalog. This does not prove all36,087 files were downloaded, all stage dependencies resolved, or the native game launched.

`asset_catalog.h/.c` connects that catalog to the existing native resolver for the iPhone/Duo/Android adapter. The native host first verifies and privately retains the immutable catalog file, then pins its original manifest SHA when opening the read-only SQLite handle. `od_asset_catalog_reference` returns caller-owned path/size/hash fields; `od_asset_catalog_resolve` returns the existing resolver's verified read-only FD. Callers cannot choose a different checksum or byte count. Player/patcher User paths, traversal, absent references and missing source files fail without network fallback. Host calls use the same serial content queue as `od_content`.

One focused host-native scenario used an actual imported game audio file (`assets/bgm/bgm_009.acb`,6,752bytes) whose APK bytes match the full export catalog. It passed catalog → SHA-verified cache → read-only FD while leaving source bytes intact; private/traversal paths and the unavailable full master failed. The first selected tutorial pack was absent from the exported-files manifest: bundled APK assets and downloaded assets are separate inputs and must not be assumed interchangeable. Compilation used the retained pinned public SQLite source after the host lacked the development linker alias. This is Linux-native content integration, not original game/Duo launch or codec compatibility proof.

SHA-256 is implemented from FIPS180-4 without platform crypto dependencies, game data or secrets. File size/hash references must come from a verified imported manifest. Hashes detect corruption, not content authenticity. The content cache is derivative verified data, not a player-save backup. Missing source/failed checks leave existing files intact. No automatic network fallback exists.

Run `python3 check_content.py` for one combined focused integrity scenario. The test uses independent Python SHA-256 and synthetic files only; it does not claim game/device execution. Both Linux, iOS and Android have the required POSIX APIs, but successful local compilation is not runtime verification on those devices.


`import_master.py SOURCE --library ../data/content --game eclipse|sparking [--activate]` creates a consistent read-only SQLite snapshot using SQLite's backup API, including committed source-WAL data. It validates integrity and required real master columns, limits the imported size, hashes the resulting snapshot and deduplicates it. Raw original database bytes need not match the normalized snapshot; the snapshot SHA is its actual content identity. No source file, player save or key is changed. Explicit activation atomically changes only the host's selection for new sessions; existing core handles/profiles keep their exact pinned content and reject mismatches. Failed validation preserves the current selection. Original game apps/encryption are not imported or guessed by this utility.

One focused importer scenario passed consistent snapshots, duplicate imports, explicit activation, unchanged source, invalid-schema rejection preserving active content, failed-stage cleanup and committed WAL inclusion. Importing the supplied Eclipse master also produced a real 17,786-card immutable snapshot in ignored cloud storage. It is not committed or claimed as physical/native/game-wire verification.

`master_archive.h/.c` adds a bounded native ZIP-container reader, linked with public/system zlib (`-lz`, Android library `z`). Call `od_master_archive_extract(sourceFD, freshOutputFD, game, &result, &error)` on a native worker. The source descriptor must be read-only, regular and seekable. The caller supplies a fresh empty, singly-linked private staging file; a published database is never a valid destination. Neither descriptor is closed. Success syncs and rewinds the output and returns its entry name, size and CRC32. Failure clears accepted output and rewinds it; the host must remove failed staging files. An already nonempty destination is rejected unchanged. No pathname, rename or master selection is performed by the reader.

For `eclipse`, exactly one of `assets/reference.db` or `reference.db` must occur. For `sparking`, exactly one of `assets/sparking-reference.db` or `sparking-reference.db` must occur. Both aliases together are ambiguous and rejected. Other entries are never extracted, regardless of their paths. Thus an APK, IPA or ZIP is usable only when its ZIP container actually contains the selected **plaintext** snapshot at an allowed path. This does not extract or decrypt an original game IPA, discover alternate paths, import game resources or obtain keys.

Before writing output, the helper checks the complete central directory, exact matching local headers, duplicate names, overlapping local records, compression flags and any data descriptors. Only stored and raw-deflate entries are supported. Encryption, ZIP64, split archives, malformed extra fields and unsupported ZIP methods/versions fail explicitly. Limits are 4 GiB minus one byte for the source, 50,000 entries, a 64 MiB central directory and 2 GiB for the selected database. Streaming uses fixed 64 KiB buffers; advertised and actual compressed/expanded lengths and CRC must agree, including an exact deflate stream end. Source bytes and descriptor offset stay untouched, and source metadata changes during extraction reject the result.

The caller must still run the existing SQLite integrity/schema/SHA importer on the extracted private staging file, and publish/select a master only after that importer succeeds. CRC detects archive corruption; it does not authenticate content. Host picker integration is separate from this portable helper.

`python3 check_master_archive.py /path/eclipse-db.zip /path/sparking-db.zip` runs the one focused combined scenario. Both supplied archives passed independent byte-for-byte SHA-256/length/CRC verification and actual read-only SQLite checks. The same batch passed stored APK-style layout, deflate data descriptors, ambiguous/duplicate/wrong-game/traversal-only archives, corruption after output streaming, encryption/ZIP64/output bounds, trailing compressed bytes and preservation of a nonfresh destination. Raw uploads and extracted databases remain outside Git; no native app build or original-game extraction is claimed.
